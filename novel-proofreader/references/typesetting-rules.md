# 版組ルール詳細

日本語商業出版小説の慣例に沿った版組調整の詳細ルールです。

## 1. 記号類の正規化

### 1.1 三点リーダー

**ルール**: 三点リーダーは `……`（U+2026 を2つ連続）に統一する。

**検出・修正パターン**:

| 入力パターン | 修正後 |
|---|---|
| `...` (ASCII period × 3) | `……` |
| `．．．` (全角ピリオド × 3) | `……` |
| `・・・` (中黒 × 3) | `……` |
| `…` (単独) | `……` |
| `………` (3連以上、奇数) | `……` または `……………`（偶数になるよう調整） |

**注意**:
- 既に `……` になっている箇所は変更しない
- 偶数個の `…` 連続は保持（`……` `…………` など）
- 奇数個の場合は1つ追加して偶数化

### 1.2 ダッシュ

**ルール**: ダッシュには Em dash `—` (U+2014) を用いる。

**検出・修正パターン**:

| 入力パターン | 文脈 | 修正後 |
|---|---|---|
| `–` (En dash) | 全般 | `—` |
| `--` (hyphen × 2) | ダッシュ意図 | `——` |
| `―` (Horizontal bar) | 全般 | `—` に統一 |
| `ー` (長音符) | 文脈上ダッシュ意図 | 文脈判断、通常は変更しない（長音符の可能性が高いため）|

### 1.3 Em dash の連数

**ルール**:
- **行頭にダッシュがある場合**: `——`（2連）必須
- **文中のダッシュ**: `—`（単独）も `——`（2連）も許容、ただし作者が一貫している場合はその方針を尊重

**判定基準**:
- 行頭: 段落の最初の文字、または鉤括弧の直後
- 文中: それ以外

**修正例**:
```
修正前: —そして彼は去った。
修正後: ——そして彼は去った。

修正前（文中、単独で許容）: 彼は—おそらく—頷いた。
修正後: 変更不要（許容範囲）
```

### 1.4 感嘆符・疑問符の後の空白

**ルール**: `！` `？` の直後に文が続く場合、全角スペース1つを挿入する。

**例外**:
- 文末（次が句点や閉じ括弧、改行）の場合は不要
- 連続する記号（`！？` `！！`）の途中は不要、連続の最後の記号の後で判断

**例**:
```
修正前: 「待って！」と彼女は叫んだ。
修正後: 変更不要（閉じ括弧の前なので）

修正前: 「待って！どこへ行くの？」
修正後: 「待って！　どこへ行くの？」

修正前: 「本当！？信じられない！」
修正後: 「本当！？　信じられない！」
```

## 2. 段落と空行の整理

### 2.1 Web小説形式の段落間1行空け

**問題**: なろう系・カクヨム系の慣行で「全ての段落の間に空行を1行入れる」スタイルは、商業出版では一般的ではない。

**ルール**: 段落間の1行空けを削除し、通常の改行のみの段落区切りに変換する。

**判定**:
- 「1行空け」= 空行（改行のみの行）が1行だけ挟まれている状態
- 「複数行空け」= 空行が2行以上連続 → **保持**（シーン転換等の意図とみなす）

**例**:
```
修正前:
　彼は森を歩いていた。

　遠くで鳥が鳴いている。

　風が梢を揺らした。

修正後:
　彼は森を歩いていた。
　遠くで鳥が鳴いている。
　風が梢を揺らした。
```

### 2.2 保持する空行・区切り

**以下のパターンは作者の意図的な区切りとして保持する**:

1. **2行以上連続する空行**
2. **区切り記号を含む行**:
   - `---` `***` `___` のような Markdown 水平線
   - `◇` `◆` `◯` `●` `※` `＊` `*` の単独行または連続
   - `* * *` `◇ ◇ ◇` のようなスペース区切り並び
   - `〜〜〜` の連続

これらは前後の空行も含めて保持する。

### 2.3 行頭の字下げ

**ルール**: 段落冒頭は全角スペース1字（`　`）の字下げを基本とする。

**例外**:
- 鉤括弧 `「` `『` で始まる段落は字下げしない
- 既に字下げ済みの箇所は変更しない（重複させない）
- ダッシュ `——` で始まる段落は字下げしない

**判定**: 段落の最初の文字を確認
- 通常文字で始まり字下げなし → 字下げ追加
- `「` `『` `——` で始まる → 字下げ不要（あれば削除）

**注意**: 一行目から字下げを意図的に省く文体もあるため、原稿全体で既に字下げが行われていない場合は、字下げを追加しない（既存方針の尊重）。判断に迷う場合は、原稿の最初の数段落の状態を確認して方針を決める。

## 3. 読点（、）の調整

### 3.1 原則

- 読点の主目的は **誤読・多義性の防止** と **構文構造（複文・重文）の境界明示** である。
- 「助詞の後だから」「息継ぎだから」で機械的に挿入してはならない。**デフォルトは「打たない」。**
- 1文あたりの読点は原則 **0〜2個**。3個以上必要に見える文は、文自体の構造に無理がある（3.5 参照）。

LLM が書いた／推敲した日本語で最も多い破綻は、文節の切れ目ごとに惰性で読点を撒くこと。特に **主題・主語の助詞（は・が）の直後に反射的に打つ** 癖が強い。この除去がこのセクションの主目的である。

> **密度で判定してはならない。** 「1文あたり平均1個程度だから適正」は誤り。1文1個でも、その1個が 3.3 の位置にあれば過剰である。判定は必ず **位置** で行う。

### 3.2 打つ読点（残す・必要なら補う）

#### ① 誤読・係り受けの混乱を防ぐとき

修飾語が直後の語ではなく、離れた語に係る場合。**これが最上位の基準**で、迷ったらこの一点だけを見る。

- × 必死な顔で逃げる男を追いかけた。（どちらが必死か曖昧）
- ○ 必死な顔で、逃げる男を追いかけた。

#### ② 重文・複文の節の境界

従属節・並列節が長く、主語や述語が切り替わる境界。接続助詞・準体助詞（が・ので・けれど・から・と・たら・ば・ても・ながら・て・か）が **長い節** を閉じる位置。

- ○ 最終日の科目が終わった瞬間、二年三組の教室には緊張の糸が切れたような空気が漂った。
- ○ 灯ちゃんの記録をどう扱うか、まだ読めない。

節が短い場合は打たない（3.3 ④）。

#### ③ 対比・並列・列挙の区切り

- ○ 一つは安全管理の徹底、もう一つは収支の透明化である。
- ○ 入域は日中のみ、単独行動の禁止、生体ログの提出義務。
- ○ 私は行かない。でも君は、行くべきだ。（対比の主題）

#### ④ 文頭の接続詞・長めの副詞句の直後

- ○ しかし、その沈黙は長く続かなかった。／ そして、まっすぐだった。
- ○ 送信ボタンを押してから、灯は静かに深呼吸をした。
- ○ 十二月最初の日曜日、摩耶先輩の部屋にその束は積まれていた。

**目安8字以上**の副詞句・状況句に限る。短い場所句・方向句は 3.3 ① に従って削除する。

### 3.3 打ってはいけない読点（既定で削除）

以下は原則すべて削除する。「作者のリズム」「意図的な間」を理由に残さない（ユーザーが明示指定した場合を除く）。

#### ① 短い主語・主題の助詞（は・が・も）の直後

主語と述語の距離が近く、構造が一目で把握できる場合は打たない。目安として主題部が助詞込み12字以内。

| × | ○ |
|---|---|
| うちは、楽勝ではない。 | うちは楽勝ではない。 |
| 窓の外は、冬の色だった。 | 窓の外は冬の色だった。 |
| 話が、あります。 | 話があります。 |
| 審査は、二週間かかった。 | 審査は二週間かかった。 |
| 灯は、目を閉じた。 | 灯は目を閉じた。 |
| 署名は、思ったよりまっすぐ書けた。 | 署名は思ったよりまっすぐ書けた。 |
| 先輩は、一枚の書式を、灯の前に置いた。 | 先輩は一枚の書式を灯の前に置いた。 |

12字を超えていても、読点なしで主題の切れ目を見失わないなら削除する。字数は目安であって免罪符ではない。

#### ② 連体修飾句と被修飾名詞の間

名詞を修飾するフレーズの直後で、名詞から切り離さない。

- × 業務連絡の顔をした、宿題だった。
- ○ 業務連絡の顔をした宿題だった。

#### ③ 助詞「の」や複合助詞の途中

- × 業務連絡、の五文字 → ○ 業務連絡の五文字
- × 四人で、週末ごとに → ○ 四人で週末ごとに
- × 申請代表者、の欄があった。 → ○ 申請代表者の欄があった。

#### ④ 短い従属節・短い状況句の直後（〜て・〜ので・〜から・〜に）

文全体が短く、意味が一息で通る場合は打たない。

| × | ○ |
|---|---|
| 一教科多くて、体感では三教科ぶん重かった。 | 一教科多くて体感では三教科ぶん重かった。 |
| この名前の下に、三人の帰りの切符がぶら下がる。 | この名前の下に三人の帰りの切符がぶら下がる。 |

#### ⑤ 目的語・補語の直後

「〜を、」「〜に、」「〜と、」は、節の切れ目でない限り削除する。

| × | ○ |
|---|---|
| 風を、辿った。 | 風を辿った。 |
| 自分の切符を、最初に数える。 | 自分の切符を最初に数える。 |
| 摩耶先輩の部屋のローテーブルに、その束は積まれていた。 | 摩耶先輩の部屋のローテーブルにその束は積まれていた。 |

#### ⑥ 短い述部の直前

文末の述部が短い（目安12字以内）なら、その直前の読点は削除する。

| × | ○ |
|---|---|
| ペンを持つ手が、少し重かった。 | ペンを持つ手が少し重かった。 |
| 先輩の声は、事務的だった。 | 先輩の声は事務的だった。 |
| 二十層の風は、これまでのどの層とも違った。 | 二十層の風はこれまでのどの層とも違った。 |

#### ⑦ 副詞・程度表現の周辺

程度・様態の副詞を読点で切り離さない。

| × | ○ |
|---|---|
| 思っていたより、ずっと分厚かった。 | 思っていたよりずっと分厚かった。 |
| 三十秒ごとに、指の本数が隊列を渡っていく。 | 三十秒ごとに指の本数が隊列を渡っていく。 |
| わたしはわりと、感情表現が豊かなのだ。 | わたしはわりと感情表現が豊かなのだ。 |

### 3.4 判定フロー

**「あるものを削るか」ではなく「無い状態から戻すか」で判定する。** 前者は既存の読点に引きずられて必ず取りこぼす。

文ごとに、次を頭の中で実行する:

```
1. その文からすべての読点を一旦外した状態を思い浮かべる。
2. 読点なしで通読し、係り受けの誤読が生じる箇所にのみ読点を1つ戻す（3.2 ①）。
3. 節（主語＋述語）の区切りで息切れ・読みづらさが出る箇所にのみ読点を1つ戻す（3.2 ②③④）。
4. 戻した位置と元の位置を比べ、元にあって戻らなかった読点を削除する。
```

3.3 の①〜⑦は、このフローで「戻らない」典型パターンの一覧である。チェックリストとして使ってよいが、**パターン照合だけで済ませず、必ず読点なしの通読を通すこと**。

### 3.5 3読点以上残る文

上記フローを経てなお読点が3つ以上戻る文は、文自体の構造に無理がある。

- **版組修正でやること**: 3.3 の削除まで。削除しても3つ以上残るなら、そのまま残してよい。
- **校正指摘でやること**: 「。」で2文に分割する案、または語順の組み替え案を **改善案として提示** する。版組修正で勝手に文を割らない。

並列列挙（A、B、C、D…）のみで構成された文はこの限りでない。

### 3.6 削除した読点の記録（校正指摘への引き継ぎ）

3.3 は機械的に適用するため、「間」を作る修辞として効いていた読点も落ちる。この効果はルールで判別できないので、**版組では削除し、削除したものを記録して校正指摘に引き継ぐ**。

記録するのは、**読点で両側から挟まれていた短い語（おおむね1〜4字）** を挟んでいた読点のみ。

例: `……五枚目が要る日のことは、まだ、誰も口に出さない。` → `……五枚目が要る日のことはまだ誰も口に出さない。`

「まだ」が両側から挟まれている＝その語に間を置く意図で打たれた可能性が高い。片側だけの読点（「思っていたより、ずっと」など）は通常の過剰読点なので記録しない。

条件を増やさないこと。「段落の最終文」「`……` を含む文」などを足すと修正箇所のほぼ全てが該当し、確認リストとして機能しなくなる。

記録は `proofreading-checks.md` 15章の形式で校正指摘ファイルに出力する。**版組修正の側で「戻すべきか」を判断しない。**

### 3.7 適用範囲

- **会話文（鉤括弧内）は変更しない。** キャラクターの話し方そのものであり、版組の対象外。
- 地の文のみを対象とする。地の文に含まれる引用符付きの短い引用（「知ってる」と繰り返す 等）も変更しない。
- 削除の前後で文意が変わらないことを確認する。変わる場合はその読点を残し、校正指摘に回す。

## 4. 適用範囲の限界

版組修正は **形式面の機械的修正** である。以下は版組修正では行わず、校正指摘（`proofreading-checks.md`）に回す。

- 文の分割・語順の組み替え（3.5 参照）
- 語句の削除・言い換え
- 表記揺れの統一（どちらに寄せるかは作者の判断）

### 修正を控えるケース

以下に限り、ルールの適用を見送ってよい。

- 原稿全体で一貫した独自スタイルが採用されている場合（例: 全文字下げなし、独自の記号体系）
- 実験的文学・詩的散文など、ジャンルとして特殊な慣行がある場合
- ユーザーから明示的に「このスタイルは保持して」と指示された項目

**この見送りはセクション3（読点）には適用しない。** 惰性の読点は文体ではなく形式の問題として扱う。

### 入力ファイルの保全

- 改行コードは入力ファイルのものを維持する（CRLF の原稿を LF に変換しない）
- 文字コードは UTF-8 のまま出力する
- 末尾の改行の有無も入力に合わせる
