# Novel Proofreader

日本語の小説・ライトノベル原稿を対象に、版組調整（自動修正）と校正・推敲（指摘）を行うスキル。

自動で書き換えるのは形式面（版組）のみ。内容面（校正・推敲）は指摘と改善案の提示に留め、判断は作者に委ねる。

## 禁止事項・必須事項（必読）

### 1. スクリプトによる一括置換の禁止

Python・sed・awk・perl・Node.js・PowerShell の `-replace` など、**スクリプトやシェルコマンドによる検索置換・一括変換は一切禁止**。「件数が多くて効率的だから」は禁止を解除する理由にならない。

**理由**: 版組ルールには「会話文（鉤括弧内）は変更しない」「区切り記号の前後は保持」「短い主題の後の読点だけ削る」など、正規表現では表現できない文脈依存の判断が多数ある。一括置換は必ず誤変換を混入させ、創作物を破壊する。

修正は必ず次の手順で行う:

1. Grep / Read で対象箇所を特定する（**検出に Grep を使うのは許可**。禁止されるのは置換の実行のみ）
2. 各箇所を文脈ごと読み、ルールの例外に該当しないか判断する
3. Edit ツール、または修正後の全文を組み立てた Write で書き換える

### 2. ファイル出力の必須化

このスキルの成果物は **ディスク上の出力ファイル** である。会話内での報告や指摘の列挙は、出力ファイルの代わりにならない。

- 版組修正を実行したら、必ず `.typeset` ファイルを Write で出力する
- 校正指摘を実行したら、必ず指摘ファイルを Write で出力する
- 指摘・修正が **0件でも**、その旨を記載した出力ファイルを生成する
- 各出力後、Read でファイルの存在と内容を確認するまで「完了」と報告してはならない

### 3. 入力ファイルの保全

改行コード（CRLF / LF）、文字コード、末尾改行の有無は入力ファイルのものを維持する。版組修正でこれらを変えない。

## 実行モード

デフォルトは「版組修正 + 校正指摘」の両方。ユーザーが「版組だけ」「校正だけ」等を指示した場合はそれに従う。

両方を行う場合は **必ず版組修正を先に実行し、校正指摘は版組修正後のファイルに対して行う**。

## 入出力

- **入力**: 原稿ファイル（テキスト形式、Markdown等。ファイル単位で処理）
- **版組修正の出力**: 元ファイルと同じディレクトリに `<元ファイル名>.typeset.<拡張子>`（元ファイルは保持）。ユーザー指定があればそちらに従う
- **校正指摘の出力**: ユーザー指定パス。指定がなければ `<元ファイル名>.proofread.md`

## 作業開始時の確認

対象ファイル／実行モード／校正指摘の出力先／作品固有ルールの有無（キャラ名表記、用語集、文体方針など）を確認する。ユーザーのメッセージから推定できる場合は確認を省略してよい。出力先が未指定でも、デフォルト名を使って処理を止めない。

## 版組修正（自動修正）

詳細なルールは `references/typesetting-rules.md` を参照。

版組修正は形式面の機械的修正であり、**「作者の意図」を理由にルールをスキップしてはならない**。例外は `typesetting-rules.md` 4章「修正を控えるケース」に列挙したものと、ユーザーの明示指示のみ。

以下の **3カテゴリ** を、カテゴリごとに **検出→修正→件数記録** の順で実行する。「該当なし」と判断する前に必ず検出を行うこと。

### 1. 記号類の正規化

**検出** (Grep):
- 三点リーダー: `\.\.\.`、`．．．`、`・・・`、`…(?!…)`（単独の …）
- ダッシュ: `–`（en dash）、`―`（horizontal bar）、`--`（hyphen 2連）
- 感嘆符・疑問符: `[！？!?][^　」』\n]`（直後に全角スペース・閉じ括弧・改行がない箇所）

**修正**: `typesetting-rules.md` 1章に従う。

### 2. 段落・空行の整理

**検出**:
- 総行数と空行を除いたテキスト行数を比較する。差が大きければ Web 小説形式の可能性が高い
- 冒頭10段落を Read し、全ての段落間に空行が1行ずつ入っているかを確認する

**修正**: `typesetting-rules.md` 2章に従う。区切り記号の行と2行以上連続する空行は保持する。

### 3. 読点の整理（このスキルの中核）

LLM が書いた／推敲した日本語では、**主題・主語の助詞（は・が）の直後に反射的に読点を打つ癖** が最大の問題になる。ここを削るのが版組修正の主目的。

読点の目的は「誤読の防止」と「複文・重文の境界明示」であって、息継ぎでも助詞の目印でもない。1文あたり0〜2個が原則。

**判定方法** — 削る対象を探すのではなく、`typesetting-rules.md` 3.4 のフローで **読点なしの状態から必要な分だけ戻す**:

```
1. 文からすべての読点を一旦外した状態を思い浮かべる
2. 誤読が生じる箇所にのみ1つ戻す
3. 節の区切りで読みづらい箇所にのみ1つ戻す
4. 元にあって戻らなかった読点を削除する
```

既存の読点を1個ずつ見て「これは要る/要らない」と判定すると、必ず元の配置に引きずられて取りこぼす。必ず「無い状態」を起点にすること。

削除対象の典型パターン（`typesetting-rules.md` 3.3 の①〜⑦）:

| # | パターン | 例 |
|---|---|---|
| ① | 短い主語・主題の は/が/も 直後 | ×窓の外は、冬の色だった。 |
| ② | 連体修飾句と被修飾名詞の間 | ×業務連絡の顔をした、宿題だった。 |
| ③ | 「の」・複合助詞の途中 | ×申請代表者、の欄があった。 |
| ④ | 短い従属節・状況句の直後 | ×一教科多くて、体感では重かった。 |
| ⑤ | 目的語・補語の直後 | ×風を、辿った。 |
| ⑥ | 短い述部の直前 | ×先輩の声は、事務的だった。 |
| ⑦ | 副詞・程度表現の周辺 | ×思っていたより、ずっと分厚かった。 |

> **やってはいけない判定**: 「1文あたり読点1個程度だから適正」「読点が3つ以上の文だけ見る」。実際の過剰読点は1文1〜2個の文に潜んでいる。文単位の個数で足切りすると、このカテゴリは丸ごと空振りする。

Grep の起点として `[はがもをにとての]、` を使ってよいが、**ヒットした箇所をそのまま消してはならない**。各箇所を文脈ごと読み、3.2「打つ読点」に該当しないか確認してから削る。

**修正**: 該当する読点を削除する。文の分割・語順の組み替えは版組修正では行わず、校正指摘に回す（3.5 参照）。会話文は変更しない。

**削除したものの記録**: 削除した読点のうち、**短い語（1〜4字）を両側から挟んでいた** もの（例: `ことは、まだ、誰も` の2つ）は、削除したうえで **位置と元の表記を控えておく**。この形は文節区切りではなく、その語に間（ま）を置く意図で打たれていることが多い。校正指摘ファイルの「15. 版組で削除した読点の再確認」に一覧で出力し、作者が目視で戻せるようにする（`typesetting-rules.md` 3.6）。版組側で「戻すべきか」を判断しない。

### 版組修正の修正順序

1. 区切り記号・複数行空行の保護（変更しない箇所を把握）
2. 三点リーダーの正規化
3. ダッシュの正規化と連数調整
4. Web形式の段落間1行空けを削除
5. 行頭字下げの調整
6. 感嘆符・疑問符後のスペース挿入
7. 過剰な読点の削除

### 版組修正の出力フォーマット

```
版組修正完了: <出力ファイルパス>

修正内訳:
- 三点リーダー正規化: N箇所
- ダッシュ正規化: N箇所
- 感嘆符・疑問符後スペース: N箇所
- Web形式空行削除: N箇所
- 行頭字下げ調整: N箇所
- 読点削除: N箇所（内訳 ①〜⑦ ごとの件数）

保持された区切り（シーン転換等）: N箇所
```

## 校正・推敲（指摘＋改善案）

自動修正せず、指摘と改善案の提示に留める。詳細な観点は `references/proofreading-checks.md` を参照。

### 指摘の観点

**積極的に拾う**: 冗長な表現／説明不足／主述の不明瞭／漢字・単語の誤用／メタ表現の混入（ファイル名、「第1話」など作品管理上の概念の本文混入。AIへの指示やチャット応答の名残、地の文の絵文字も含む）／表記揺れ／視点（POV）のブレ／時制の不自然な混在／口調・一人称の揺れ／修飾語と被修飾語の距離／「の」の3連鎖／受動態の濫用・二重否定／成り立たない比喩（主語と述語だけを取り出すと意味が通らず、何を例えたのか連想できないもの。読み取れる比喩は対象外）

**控えめに指摘**: 文章のリズム、段落・シーン構成、場面ごとに同じ型で繰り返される内面の説明。版組修正後になお読点が3つ以上残る文と、100文字超の長文もここで扱う（「。」での2文分割、または語順の組み替え案を提示する）

**必ず全件出力する（指摘ではなく確認リスト）**: 版組で削除した読点のうち「間」の修辞だった可能性があるもの（`proofreading-checks.md` 15章）。絞り込まず、判断も書かず、候補をそのまま列挙する

**最低限に留める**: 指示語（あれ・これ・それ）— ファイル単位ではコンテキストが限定的なため

### 校正指摘の出力フォーマット

`references/proofreading-checks.md` 末尾の「出力フォーマット」に従う。カテゴリごとにまとめ、重要なもの・修正コストが低いものを上位に置く。

## 作品固有ルールの扱い

ユーザーから提供された作品固有のルール（キャラ名一覧、用語集、文体方針、`expression-rules.md` 等）は、校正指摘の参照基準として最優先で利用する。表記揺れ検出の基準、文体方針の遵守チェック、禁則表現の検出に使う。

ルールがない場合は、本文内での自己整合性のみをチェックする（例: 同じ名前が「アリス」と「ありす」で混在していないか）。

## 処理の流れ

### ステップ 1: 読み込み
原稿ファイル、作品固有ルール、`references/typesetting-rules.md`、`references/proofreading-checks.md` を読み込む。

### ステップ 2: 版組修正の事前検出（省略不可）

3カテゴリそれぞれについて実際にファイル内を調べ、問題箇所の有無と規模を把握する。

```
事前検出結果:
- 記号類: 三点リーダー異常 0件, ダッシュ異常 0件, 感嘆符後スペース 2件
- 段落・空行: Web形式空行あり (推定 200行), 字下げ異常 0件
- 読点: 地の文 103文 / 読点 115個。うち削除対象 67箇所（①38 ②2 ③1 ④7 ⑤9 ⑥14 ⑦6）
- 改行コード: CRLF（出力でも維持）
```

読点カテゴリで「0件」と報告する前に、`[はがもをにとての]、` の Grep 結果を実際に1件ずつ確認したかを自問すること。地の文が数十文ある原稿で削除対象0件になることは、まずない。

### ステップ 3: 版組修正の実行

事前検出の結果に基づき、「版組修正の修正順序」に沿って修正する。Edit / Write ツールのみを使う。

### ステップ 4: 版組修正の出力検証（省略不可）

出力ファイルの冒頭30行程度を Read し、次を確認する:

- [ ] 出力ファイルがディスク上に存在するか
- [ ] 段落間の空行が削除されているか（Web形式空行があった場合）
- [ ] 区切り記号の前後の空行が保持されているか
- [ ] **読点の削除が実際に反映されているか**（事前検出の件数と突き合わせる）
- [ ] 会話文の読点が変わっていないか
- [ ] 改行コードが入力と同じか
- [ ] タイトル行や字下げが崩れていないか

検証に失敗した場合は、該当箇所を修正して再出力する。

### ステップ 5: 修正サマリの報告

「版組修正の出力フォーマット」に従って件数付きで報告する。

### ステップ 6: 校正指摘の実行

`references/proofreading-checks.md` を参照して問題箇所を抽出し、カテゴリ別に整理して **必ず指摘ファイルに Write で出力する**。会話内での概要報告は、ファイル出力が完了した **後** に行う。

### ステップ 7: 完了確認（省略不可）

- [ ] 版組修正ファイル（`.typeset`）が存在し、ステップ4の検証を通ったか
- [ ] 校正指摘ファイルが存在し、Read で内容を確認したか
- [ ] 版組で読点を削除した場合、「15. 版組で削除した読点の再確認」を校正指摘ファイルに出力したか
- [ ] 修正・指摘の件数をユーザーに報告したか

このチェックを通過するまで完了報告をしてはならない。

## 複数ファイルの処理

複数ファイルは Agent ツールで並列処理してよい。各エージェントには以下を渡す:

- 担当ファイルのパスと出力先パス
- `references/typesetting-rules.md` を読むよう指示（ルールを要約して渡さない。特に読点ルールは要約すると空振りする）
- 会話文は変更しない旨
- スクリプト・コマンドによる一括置換は禁止、修正は Edit / Write のみ
- 出力ファイルの生成は必須で、生成後に Read で存在確認する旨
- 事前検出の件数と修正後の件数を報告させる

エージェント完了後、出力ファイルの実在を確認し、ステップ4の検証を必ず行う。エージェントが「完了した」と報告していてもファイルが無ければ未完了として処理し直す。読点の削除件数が0で返ってきた場合も、検出が空振りした可能性が高いので自分で再確認する。

## 校正・推敲での注意

- **創作物の尊重**: 文体、リズム、独特な表現は作者の意図である可能性が高い。明らかな誤りや一貫性の欠如以外は指摘しない
- **過剰指摘の回避**: 全ての箇所を指摘せず、改善効果の高いものに絞る
- **作中の世界観優先**: 意図的な造語や古めかしい表現を誤用として扱わない
- **小説として普通の書き方は指摘しない**: 会話の話し言葉、読み取れる比喩、短い文の連続、言いさしのダッシュや三点リーダー、語り手の主観、作者がわざと残した複数の読み（`proofreading-checks.md` 16.3）
- **改善案は意味を変えず、何も足さない**: 何を言っているか・何に重きを置いているか・言い切りの強さ・文の種類を元の文と同じに保つ。前後の文にない動作・感覚・気持ち・理由を書き足さなければ書けない場合は、改善案の代わりに作者への確認を書く。改善案が「街灯がただ黙って道を照らしていた」のような別の AI 調の形になったら、その案を捨てる（`proofreading-checks.md` 末尾「引用と改善案」）

なお、この「作者の意図の尊重」は校正・推敲に適用される方針であり、版組修正（特に読点の整理）には適用しない。
